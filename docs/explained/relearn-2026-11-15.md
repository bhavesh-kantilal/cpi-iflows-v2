## 2. Patterns in your originals that we don't use yet
1. **Grouping and summing with standard functions** (ACC, ACC_OTM, INV):
   - **distinct values:** `TAX_CODE ← FixValues(SplitByValue[each](collapseContexts(SplitByValue[value change](removeContexts(taxCode)))))`
   - **sum per group:** `AMT_DOCCUR ← SplitByValue(sum(formatByExample(amount, SplitByValue[value change](removeContexts(taxCode)))))`
   - This is grouping by **consecutive equal values** without a UDF. DESADV uses a UDF (`groupByHeat`) for a similar job (Q1).
2. **`context=` on element fields to collapse a repeating condition into one context** (73 element contexts in L1, 45 of them in INV; mostly 2 levels up). We now use `removeContexts` for that (Q3).
3. **`counter`** for item numbers (ACC, ACC_OTM, JE, INV: 24×), e.g. JE `ReferenceDocumentItem ← counter`.
4. **valuemap** lookups against Value Mapping artifacts (ACC, JE, SUP), with "use default value" and defaults `NF` / `N/A`. All our mappings use inline FixValues (ORDERS VM tables) instead.

## 3. Questions to you (each answer becomes L2 evidence)
- **Q1 — Grouping (ACC `ACCOUNTTAX/item/TAX_CODE` and `CURRENCYAMOUNT/item[2]/AMT_DOCCUR`).** Is this chain meant to give one value per **distinct tax code**? SplitByValue "Value change" only groups *consecutive* equal values: are the tax lines always sorted by tax code (sorted by Medius, or are equal codes always adjacent)? If DESADV bundles of one heat are always adjacent, could we drop the `groupByHeat` UDF for this pattern?
- **Q2 — Sum per group (same targets).** Is `sum(formatByExample(amount, SplitByValue[value change](removeContexts(taxCode))))` "the sum of the amounts per tax code"? This would be the standard way to do the DESADV metres/weight sums.
- **Q3 — `context=` vs `removeContexts`.** JE sets `taxCode` to context `/root/invoice` so that `createIf` on `ProductTaxItem` sees all tax lines in one context. ORDRSP uses `removeContexts` after the filter for the same effect. Do you prefer one style for new mappings?
- **Q4 — `mapWithDefault` after a context change (ACC `CURRENCYAMOUNT/item[6]`, `customField_Numeric1 ctx /root`; SUP `identifiers`, `BankAccountID ctx BusinessPartner`).** Here it's used on purpose. Is the rule "OK when the field occurs at most once per (new) context; not OK when one context holds several occurrences with gaps"?
- **Q5 — `counter` (JE `ProductTaxItem/ReferenceDocumentItem`, ACC item numbers).** Is the counter reset per document (one message = one document) by design, and is this your standard for line numbers?
- **Q6 — MAT `Descriptions/Description/@lang` ← `toUpperCase(Description/@languageCode [ctx Product/Description])`.** Why the context on the language attribute here? To pair it with the right Description when several exist?
